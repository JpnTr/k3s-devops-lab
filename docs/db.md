# Database and data lifecycle

Use PostgreSQL database `orders` with a dedicated application role and a separate bootstrap/migration step. Bootstrap creates the role when needed and reconciles its password from the private Secret on every run, repairing application-role/Secret drift. The controller creates credentials before cluster creation and refuses to regenerate them when recorded lab state indicates a cluster may retain a PVC; restore the private credentials file or tear down the dedicated cluster and its data before starting fresh. Store id (generated primary key), sku (bounded text), quantity (positive integer), created_at (timestamp with time zone), and a unique nullable fixture key. The three fixture rows use stable keys and the bootstrap insert is idempotent. Generated traffic rows have no fixture key; after each insert the API prunes rows beyond a target of 1,000 generated orders, retaining all fixtures. Concurrent inserts may temporarily race around this target and need load verification. The PVC requests 2 GiB; that request is not a storage quota. These are authored targets, not measured storage or performance guarantees.

Use transactions and parameterized queries. `make lab-reset` restores workload settings and retains orders; repeated `make up` reuses the PVC and stable generated credentials. `make down CONFIRM=yes` deletes the cluster, PVC, and its database contents, removes credentials and kubeconfig files, and leaves a minimal absent lifecycle record and mutation lock in `.lab/`. The deployment sets a maximum pool of five; the API defaults to a two-second pool-acquisition timeout and three-second statement timeout. Pool capacity, in-use connections, acquisition wait, and timeout metrics are exposed. Fresh install, restart with an existing PVC, fixture retention, pruning behavior, and actual PVC use still require runtime checks.
