# Incident catalog

Each ID ships with metadata (title, level, prerequisites, maximum duration), a student brief, three progressive hints, instructor notes, a scoped patch, a symptom detector and an independent recovery check. Give hints in order: layer, evidence source, focused inspection. Use the matching baseline manifests or recorded state to restore changes. Keep the fault patch local and reversible.

| ID | Fault and expected impact | Evidence and recovery requirement |
| --- | --- | --- |
| 01 | Change the API Service selector to `app.kubernetes.io/name=deliberately-absent`. Ingress loses the API backend. | Require that exact selector, two Ready pods, and zero ready EndpointSlice addresses. Restore the selector. Verify eligible endpoints and repeated ingress 200s. |
| 02 | Change the readiness path to `/wrong-ready-path` in a rollout. New pods run but remain unready. Use a rolling strategy that keeps old replicas available. | Require the faulted probe path, an unready replacement, two Ready old replicas with ready endpoints, and a successful Orders request. Correct the path. Verify updated replicas ready and ingress stays healthy. |
| 03 | Set `DB_HOST` to `postgres-missing.lab.svc.cluster.local`, a nonexistent name within the lab Service DNS zone. Requests to orders fail with a dependency error. | Require the configured fault host, exactly one Ready PostgreSQL pod, healthy `/livez`, and an indexed `db_dns_error` for the exact failed request. Compare failed lookup with a successful PostgreSQL Service lookup from the API namespace. Verify database-backed GET and absence of fresh DNS errors after repair. |
| 04 | Change the ingress host rule to `wrong.lab.test` while continuing to send the original Host header. | Require the configured fault host, a host-level 404, and a successful direct Service request. Restore the route and verify the correct host and path. |
| 05 | Deploy synthetic v2 with `FAULT_FAIL_PERCENT=35`. Keep the process and probes healthy. | Require v2 plus the configured failure rate and an indexed `synthetic_failure` for an exact failed request. Filter failures by version and inspect rollout history. Restore v1 with no failure rate, then verify success while retaining old evidence. |
| 06 | Set `FAULT_DELAY_GET=0.8` on GET /orders. Preserve successful responses. | Require the configured delay plus a successful request taking at least 700 ms. Compare route p95 with historical baseline and trace slow request IDs in Kibana. Remove delay and verify p95 recovery after the query window clears. |
| 07 | Reduce effective DB pool capacity and use a bounded burst plus deterministic connection hold time. | Compare pool wait and timeouts against API failures. Restore pool and traffic settings. Verify normal requests and a recovery burst without timeouts. |
| 08 | Set API memory limit to 128 MiB and bounded startup allocation to 512 MiB in a lab variant. Keep other components isolated from the memory test. | Require both fault settings and an API container's `OOMKilled` last termination reason. Previous logs are optional evidence. Restore the baseline and verify no new restarts over an observation window. |
| 09 | Set the API worker selector to `lab.k3s-devops.invalid/worker=nowhere`, matching no worker. Preserve old replicas during the stalled rollout. | Require a Pending replacement, two Ready old replicas with ready endpoints, and a successful Orders request. Inspect scheduling events. Restore placement and verify rollout completion and new ready endpoints. |
| 10 | Change Fluent Bit's output to stdout instead of Elasticsearch. Leave API and Elasticsearch healthy. | Require the stdout output configuration, healthy Elasticsearch, a fresh successful request ID in API stdout, and absence from Elasticsearch. Restore collection and verify a new ID arrives without relying on backfill. |
| 11 | Change the API scrape path to `/missing-metrics` while scrape remains enabled on port 8000. Preserve app traffic and logging. | Require that configured scrape, a down Prometheus target, successful API traffic, and an indexed request log. Restore the path and baseline scrape annotations, then require healthy target and fresh application metrics. |
| 12 | Cordon and drain a verified lab worker. Preflight replica placement, eviction constraints and rescheduling headroom. | Require one Ready API replica and a Pending replacement before activating the exercise; the surviving replica must continue serving. Uncordon and restore placement policy and both replicas. Verify the node is schedulable, replicas are Ready on separate workers, and requests succeed. |

For 05, 06, and 07, record the start and recovery traffic windows and use bounded retries to distinguish stale data from live faults. Lab 12 uses only the dedicated lab worker and normal eviction behavior. Capture partial progress and ensure reset uncordons the exact node even if drain times out. Each scenario must pass twice consecutively without a cluster rebuild. Teach negative controls as part of each lab, such as a healthy Service path during an ingress problem.
